## 🔴 権限(`admin`/`editor`, 2026-08-03導入・2026-08-04に削除を追加)

`admins`シートの`role`列で2種類。

| 操作 | `admin` | `editor` |
|---|---|---|
| 大会の作成・保存・情報更新・終了 | ✅ | ✅ |
| **大会の削除(アーカイブ)** | ✅ | **❌** |
| ユーザーの新規追加 | ✅ | ✅ |
| 既存ユーザーの変更(撮影可否・アーカイブ・並び順) | ✅ | ❌ |
| **アーカイブ済みユーザーの閲覧・復元** | ✅ | **❌** |

- 実体は`gas/Code.gs`の`canManageUsers_(role)`と`canDeleteTournament_(role)`。`assertAdmin_`が role を小文字化して返し、**空欄は従来どおり`admin`**(既存管理者をロックアウトしないため)、**`admin`以外の文字列は最小権限側=`editor`**に倒れる
- **大会の削除だけ`admin`限定にしたのは、1件ぶんの対戦結果がまとめて一覧から消える操作だから。** 保存・情報更新・終了は当日の運営が止まるので絞っていない
- ⚠️ **権限不足を`authError_()`で投げないこと。** それは`code:'FORBIDDEN'`になり、クライアントが**再ログインを促す**導線(`needsAuth`)に使う。`editor`に「再ログインすれば直る」と誤解させるので、`permissionError_()`で`code:'PERMISSION'`を返す
- クライアントの`AtsuCup.isAdmin()`は**UIの出し分け専用**。`GasDB.getRole()`(sessionStorageのキャッシュ、`ping`の応答で埋まる)を見るだけなので、偽装してもサーバーで弾かれる
- 🔴 **`AtsuCup.isAdmin()`を使うページは、必ず`GasDB.ensureRole().then(再描画)`を呼ぶこと。** `isAdmin()`は`GasDB.getRole()`(sessionStorageのキャッシュ)を見るだけで、`ensureRole()`を一度も呼ばないと**常にnullのまま=adminでもUIが出ない**。現在呼んでいるのは`users.html`と`detail-view.js`
- ⚠️ **role未確定(ping応答待ち)の間は false に倒すこと。** admin UIが一瞬出てから消えるより出さない方が誤操作が無い。確定してから描き直す
- ⚠️ **`editor`の既存行変更をエラーで弾かないこと。** クライアントは毎回ロースター全件を送るため、他端末でadminが変更した直後の`editor`端末は古いキャッシュの値を送ってくる。エラーにすると**大会中の飛び入り登録まで止まる**。黙って無視すれば、`editor`の古い値でadminの変更を巻き戻す事故も同時に防げる(無視した名前は戻り値`ignoredChanges`に入る)
- 飛び入り参加者は大会保存時に`ensureUsers_()`がサーバー側で採番するので、**`editor`でも当日の運用は回る**
- ⚠️ 未ログイン(練習モード)は**基本的に権限の概念が無い**。ゲストプールはこの端末だけのデータなので、`users.html`の`canEditUsers()`は`isGuestMode() || isAdmin()`で判定する。ここを`isAdmin()`だけにすると練習モードで何も操作できなくなる

### アーカイブ済みユーザーの閲覧は admin のみ(2026-08-04)

`users.html`の権限判定は役割で2つに分かれている。

| 関数 | 条件 | 制御する対象 |
|---|---|---|
| `canEditUsers()` | `isGuestMode() \|\| isAdmin()` | 📹撮影可否トグル・☰ドラッグハンドル・保存バー |
| `canViewArchive()` | **`isAdmin()`のみ** | 📦アーカイブ・♻️復元・「アーカイブ済みを表示」の開閉ボタン・アーカイブ一覧 |

⚠️ **📦アーカイブも必ず一緒に隠すこと。** 開閉ボタンだけ隠して📦を残すと、アーカイブはできるのに一覧に出ず復元もできない**「戻せない」詰み**になる。

⚠️ この分離により、練習モードで既にアーカイブ済みのゲストユーザーは見えなくなる(`orderedRoster()`がアーカイブ済みを除外するため一覧にも出ない)。ゲストプールはログイン時に`clearGuestPool()`で消える性質のものなので実害は小さい。

## 🔴 ユーザーの並び順(`sortOrder`, 2026-08-03)

`users`シートの最終列に`sortOrder`(num)を追加し、ユーザー管理画面のD&Dで決める。参照するのは**ユーザー管理・大会エントリーの候補一覧/選択中の表示・飛び入り参加の候補**。

- 並べ替えは`AtsuCup.orderedRoster(P)`に一本化(sortOrder昇順 → 同値は`roster`配列順。`Array.prototype.sort`は安定)。**全員0(列追加前のデータ)なら従来とまったく同じ並び**になるので移行作業は不要
- 新規登録時は`user-register-modal.js`が**既存の最大値+1**を振る。振らないと0のままになり、並べ替え済みの環境で新規ユーザーが一覧の先頭へ飛ぶ
- D&Dの確定時(`commitOrderFromDom`)はアクティブに1..N、続けてアーカイブ済みにN+1..を振る。アーカイブ済みを0のまま放置すると、復元した瞬間に先頭へ飛ぶ

🔴 **`state.people`の配列順は絶対に変えないこと。** `fromAppTournament`の`entryRows`は`t.people`の順に作られ、その配列は`syncSignatureOf`の`stableStringify`に**順序込みで**入る(stableStringifyが並べ替えるのはオブジェクトのキーだけで、配列要素は並べ替えない)。並べ替えると全大会の署名が変わり、**全端末で競合モーダルが誤爆する**。エントリー画面の「選択中」は`sortedForDisplay()`で**描画用のコピー**だけを並べ替えている(実データで署名が変わらないことを確認済み)。

## 🔴 ユーザー管理は保存ボタン方式(2026-08-03)

以前は撮影可否・アーカイブ・復元・新規登録の**すべてが操作の都度サーバーへ送信**していた。D&Dの並べ替えを都度送るとGAS実行とGitHubコミットが乱発するため、**ローカル即時保存 + 保存ボタンでサーバー送信**に統一した。各操作は`AtsuCup.persist()`でこの端末には即座に残るので、**画面を離れても未保存の変更は消えない**(サーバーに出ていないだけ)。

⚠️ **保存ボタン方式にするなら、マージ保護がセットで必須。** `mergeRemoteUsers()`は`Object.assign`でリモート値をローカルへ無条件に被せる作りで、**毎ページ読み込みで走る**。即時保存だった頃は窓が狭くて表面化していなかっただけで、そのままだと未保存の編集が黙って消える。

- `usersSignatureOf()` … `[name, recDefault, archived, sortOrder]`を**名前順**に並べた正規形。⚠️ `roster`配列の順序に依存させないこと(並び順の情報は`sortOrder`が持っており、配列の並びは端末ごとに違いうるため)
- `state.remoteUsersSig` … この端末が最後に把握しているサーバーの内容の署名。`mergeRemoteUsers`はローカル署名がこれと違う(＝未保存)なら**取り込みを丸ごと見送る**。大会側の3分類マージの「この端末だけ変更 → 何もしない」と同じ考え方
- `saveUsersToData()`成功時に**送った内容の署名**で基準値を更新する。これをしないと保存直後から「未保存」と誤判定され、他端末の更新を取り込むマージが永久に止まる
- `migrate()`で`remoteUsersSig`が無い旧キャッシュは**nullのまま**にする(現在値を入れると、実際はサーバーと違うのに「未保存なし」と誤認して他端末の更新前に上書きしうる)
- 保存バーは`.atsucup-save-bar`。`bottom:var(--atsucup-bottom-bar)`でセッション切れバナー(9997)の**上に**積み、z-indexはその1つ下(9996)。body余白のルールは`.atsucup-has-session-banner`より**後ろ**に置く(両方付いた時に合計値が勝つ必要がある)

**割り切り**: 2端末が同時に別々のユーザーを編集すると後勝ちになる(`actionSaveUsers_`は名前単位のフィールド更新なので、他端末の**追加**は残る)。大会側の「ほぼ同時保存は検知できない」と同じクラスの制限。

## 「公式大会」「制限杯」フラグ（2026-07-27 導入）

`tournaments`に`isOfficial`/`isRestricted`の2つの真偽値フラグを追加した。大会作成・編集フォームのトグルボタンでオン/オフでき、通常の進行状況保存のたびにサーバーへ反映される。**集計ロジック(戦績・歴代優勝者)への組み込みは未実装**(将来の対応、現時点は保存・表示のみ)。表示は大会一覧・TOPの開催中大会・大会詳細のバッジで、**公式大会→制限杯→進行中/完了→ローカルの順**に固定。

## 🔴 戦績の集計対象は「公式大会のみ」(2026-07-29に変更)

`record.html` / `record-detail.html` は **`🏅公式大会` フラグが立った大会だけ**を集計する。その中を3つに絞り込める。

| ボタン | `scope` | 条件 |
|---|---|---|
| 🏅 全て(既定) | `official` | `isOfficial` |
| 🔒 制限杯のみ | `restricted` | `isOfficial && isRestricted` |
| 🏅 制限杯をのぞく | `nonRestricted` | `isOfficial && !isRestricted` |

⚠️ **今後作る大会も「🏅公式大会」をONにしないと戦績に入らない**(`newBlankTournament` の既定は `false`)。非公式大会(ゲリラ等)は戦績・ランキングから完全に外れる。これは意図した仕様。

**`allFinishedEntries(opts)` は引数を省略すると従来通り全大会を返す。** 絞り込みは呼び出し側が `opts` を渡した時だけ効く。`scope` の3値はいずれも `isOfficial` を織り込んであるので、呼び出し側が公式判定を別途書く必要はない。`computeAllTimeStats(opts)` はそのまま素通しする。

**アーカイブ済みユーザーはランキングに出さない(2026-08-03)。** `computeAllTimeStats` が返す直前に `state.archivedUsers` で除外する。⚠️ **`state.roster`を種にするループだけを絞っても不十分**で、過去大会の参加者から `ensure()` 経由で復活してしまうため、**返す直前でフィルタする**こと。他の人のポイント・順位はこの除外の影響を受けない(ポイントは大会ごとに導出しており、集計対象の人数に依存しない。実データで除外前後の全項目が一致することを確認済み)。`record-detail.html`(個人ページ)は**変更していない** — 一覧に出ないだけで、URLを知っていれば過去の戦績を追える。

## 🔴 勝率・優勝率・4強率(2026-08-03追加)

`record.html` の各行に「回数」と「率」を2行で出し、並び替えに **Pt順(既定)/勝率順/優勝率順/4強率順/名前順** を用意した。絞り込みUIは `<details>` のアコーディオン(`.filter-acc`)に集約し、**閉じている時もヘッダに現在の状態を出す**(開かないと何順か分からなくなるため)。

| 指標 | 定義 |
|---|---|
| 勝率 | 実戦勝利 / 実戦数 |
| 優勝率 | 優勝回数 / 出場回数 |
| 4強率 | (優勝+準優勝+3位+4位) / 出場回数 |

**「実戦数」(分母)は「実戦勝利」(分子)とまったく同じ条件で数える。** `computeAllTimeStats` の
`countGame(a, b, winner)` が1回の呼び出しで `games` と `wins` の両方を進めるため、定義上ずれない:

```js
const countGame = (a, b, winner)=>{
  ensure(a).games++; ensure(b).games++;   // 分母: 対戦した2人ぶん
  if(winner) ensure(winner).wins++;       // 分子: 勝った1人ぶん
};
```

つまり **1つの対戦につき、分母は2人に+1、分子は勝者だけに+1**。条件を満たさない枠（BYE・
不戦勝・未決着・片側しかいない枠）は**分母にも分子にも入らない**。
⚠️ 分子と分母で条件を分けて書き直さないこと。片方だけ変えると勝率が1を超えたり食い違ったりする。

**「勝利/出場」は採用していない。** シングルエリミネーションでは敗北がほぼ1回に固定される(実データで476敗/出場延べ484=0.98)ため、勝率≈A/(A+1) という単調変換にしかならず、順位相関0.977で**同じことを言っている**。読みやすい「勝利/対戦」だけを出す。

🔴 **勝率の勝利数は `entries.wins`(=`countWins()`)を使わず、`computeTournamentPoints` と同じ `m.a && m.b && m.winner && !m.bye` で数え直す。** `countWins()`は`!bye`を見ておらず、`pickWinnerAsSeed`(両者そろった不戦勝)が使われるとPと勝率が食い違う。現データでは一致(476=476)しているが、それは同機能の実使用がまだ無いだけ。3位決定戦は`entry.matches`の外なので別途加算する(こちらは既存挙動に合わせて`!bye`を見ない)。

🔴 **最低出場回数(なし/5回/10回)の判定は「期間の絞り込みを無視した出場回数」で行う**(scopeは尊重)。期間内の出場回数で判定すると、**直近3ヶ月(4大会)に絞った瞬間に該当者が0人になり一覧が空になる**。全期間ベースなら実測で 直近3ヶ月×10回以上でも13人残る(90通りの組み合わせすべてでランク0件にならないことを確認済み)。`record.html` が `computeAllTimeStats({scope})`(期間なし)をもう一度呼んで基準にしている。

- ランクに出る条件 = `全期間の出場回数 >= しきい値` **かつ** `絞り込み後の実戦数 > 0`(後者が無いと、その期間に1度も出ていない人が勝率「—」でランク内に並ぶ)
- **満たさない人は除外せず末尾へグレーでまとめる**(`.rank-row-dim`)。誰も消えないので期間を絞っても空にならない
- 既定は**「なし」**。⚠️ そのため率で並べた直後は出場1回の人が1位に出る(タロ100%等)。これは仕様で、しきい値で絞ると実力順に近づく

⚠️ **率の同値には必ずtie-breakを入れること**(Pt降順 → 名前順)。優勝率は0%が47人中32人いるため、無いと並びが不定になる。
⚠️ **分母0は0%ではなく`—`にする**。0%にすると「まだ戦っていない人」が「全敗した人」と同じ見え方になる。
⚠️ **🥇🥈🥉はPt順のときだけ**。他の並びで金メダルを出すと優勝者と誤解される。名前順は番号なし(従来どおり)。
⚠️ 状態は`sort`/`min`もURLクエリで持ち回る(既存の`scope`/`from`/`to`と同じ理由)。個人ページは使わないが**戻った時に一覧の見え方を復元するため素通しする**。

**日付入力欄**: `.date-field-row`で**縦積み**にし、枠内右端に📅を重ねた(`.date-input`)。横並びだと375pxで潰れて読めなかった。⚠️ **`appearance:none`は外さないこと**(iOS Safariのネイティブ日付UIが`width:100%`を無視してはみ出す実機バグの対策)。そのためネイティブのカレンダーアイコンが出ず、**自前の要素を重ねている**。ネイティブの`::-webkit-calendar-picker-indicator`は非表示にしているので、**デスクトップで開く導線が消える。📅アイコンのclickで`showPicker()`を呼んで補っている**(未対応ブラウザでは`focus()`にフォールバック)。

🔴 **iOS実機で発覚した2つの不具合(2026-08-03に修正)。同じ構造を書く時は必ず踏襲すること。**

1. **`min-height`が無いと枠が潰れる。** iOS Safariは`appearance:none`かつ値が空だとinputの中身を何も描画しないため、高さが`padding`分(≒20px)まで縮む。デスクトップChromeは`----/--/--`を描くので**気づけない**。`.date-input input[type="date"]`に`min-height:44px; line-height:24px`を入れてある
2. 🔴 **期間の変更で`renderFilter()`を呼び直してはいけない。** inputごと作り直すことになり、**開いているネイティブの日付ピッカーが閉じる**。iOSでは「タップ→ピッカーが開く→今日の日付が自動で入る→changeで再描画→閉じる」となり、**2回タップしないと目的の日付を選べなかった**。`refreshAfterFilterChange()`で、見出しの状態表示と件数だけをその場で書き換えて一覧を描き直す
   - 併せて **`showPicker()`はinput本体ではなく📅アイコンにだけ**付けること。inputに付けるとタップで開くネイティブのピッカーと二重に走る。したがって`.date-icon`に`pointer-events:none`を付けてはいけない

⚠️ **期間の既定値は入れていない。** `2025-01-01〜当日` を検討したが、**開催予定の大会を先に作って開催日を未来にする運用が想定されている**ため、`to`=当日 だとその大会が集計から漏れる。

**削除(アーカイブ)した大会は戦績に影響しない(2026-08-03に実データで確認)。** `atsucup-data.js`の`toAppTournaments()`が`!t.archived`で除外し、さらに`loadFromData()`がフェッチした生データから`archived===true`のidを`state.tournaments`から問答無用で取り除く二重の防御になっている。実データではアーカイブ済み大会が2件(第32回の重複作成。片方に12エントリー・16対戦・勝敗16件が残っている)あるが、`record.html`の表示は「公式大会 31件」＝*公式かつ非アーカイブ*と一致しており、漏れていない(漏れていれば33件になる)。シートに残る entries/matches は復元可能性のための意図的な保持。

⚠️ **期間の比較は `dateInputValueOf()` で `YYYY-MM-DD` に落としてから文字列比較すること。** `createdAt`(=シートの `heldAt`)は **JSTのその日の0時をUTCで表した値**(例: 6/27開催 → `2026-06-26T15:00:00.000Z`)。`Date` の数値で比較すると境界日が1日ずれる。

⚠️ **絞り込み状態はURLクエリ(`scope`/`from`/`to`)で持ち回る。** 一覧→個人ページの遷移でも引き継ぎ、戻るリンクにも付ける。これをしないと**ランキングのPと個人ページの通算Pが食い違う**。手打ちURL対策として、未知の `scope` は `'official'` に倒し、`YYYY-MM-DD` 形式でない日付は空として捨てる(捨てないと「常に0件」の詰みになる)。

絞り込みボタンは大会一覧のバッジと同じ `.flag-toggle-btn official/restricted` の `on`/`off` を流用しており、**このために新規CSSは書いていない**。

(2026-07-29に `hall.html`(歴代優勝者)を削除。`championEntries()` も専用だったので撤去した。**カード描画一式(`generateAndSaveCard`/`drawCard`/`themeForTitle`/`THEMES`)は `results.html` の「優勝カードを作る」がまだ使うので残してある**)

## モンスター別集計(2026-08-08追加)

`record.html` の「02 モンスター別」は、`AtsuCup.computeMonsterStats(opts)` の結果を出す。

- **母数は戦績ランキングとまったく同じ** — `allFinishedEntries(opts)` を再利用しており、上の絞り込み(対象の大会・期間)がそのまま効く
- 🔴 **`computeAllTimeStats` には手を入れていない。** 既存の戦績(ポイント・順位・勝率・件数)の値が1つも動かないことが要件だったため、独立した関数として実装した(実データで新旧の全項目一致を確認済み)
- **`monsterId` が未設定のエントリーは集計に入れない。** 「未設定」という架空の1体を作らないため。結果として **使用回数の合計 ≠ 参加者数の合計** になるが、これは正しい状態
- **マスタから消えたidも落とさない。** `monsters.json` に無い `monsterId` は「不明なモンスター(id)」として1行で出る(黙って消すと、集計から抜けた理由が誰にも分からなくなる)
- **勝率の数え方は `computeAllTimeStats` の `countGame` と完全に同じ条件**にしてある(`m.a && m.b && m.winner && !m.bye` + 3位決定戦)。両画面で勝率が食い違うと、どちらが正しいのか判断できなくなるため
- オーラ色別・モン類別の内訳は、**同じ集計結果を足し上げるだけ**にしてある(別ルートで数え直すと一覧と内訳が食い違いうる)。`MONSTER_AURAS`/`MONSTER_KINDS` に無い値は「その他」にまとまる

エントリー時のモンスターの記録先は `entries.monsterId`(`data/SCHEMA.md`)。入力できる場所は
大会エントリー画面・途中参加(飛び入り)・大会詳細の「参加者とモンスター」の3箇所で、
**大会詳細からの変更は対戦開始後もできる**(エントリー画面は1回戦決着後にロックされるため、
そこが唯一の修正導線になる)。⚠️ ただし**参加者の追加/削除の導線をそこに作らないこと** —
エントリー画面のロックは進行中の対戦結果を `resetDownstream()` で壊さないための設計で、
抜け道を作ると同じ事故が起きる。
